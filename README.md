# J.C.
Daily AstroParticle Physics Journal Club

## Edit a report or history section

Edit the dated source file in [`content/`](content/), for example
[`content/2026-09-16.md`](content/2026-09-16.md). Below the JSON metadata,
the report is ordinary Markdown. Search for `##### History` in reports from
22 September onward, or `**Assessment:**`, `**Classification:**`, or
`**Significance:**` in older reports, to find the literature context and comments.
You can rewrite or remove those paragraphs. They are part of the report text,
not judgments generated by the website.

From 22 September onward, retain each source assessment under a nested
`##### History` heading instead of the `**Assessment:**` label. Preserve its
literature references, scientific comparisons, and limitations, using the same
public-facing prose as the main summary. Earlier reports retain their existing
content unless a separate change is requested.

The build reads the same report body for the dated page, full-text search,
Markdown download, and offline archive. Assessments have no separate copy in
the source metadata. Paper `teaser` fields control the short search excerpts.

After editing, rebuild with Python 3.10 or newer:

```sh
python3 scripts/build_archive.py
```

Commit the source and regenerated files together, then push to GitHub.
The repository root remains the publishable site for GitHub Pages configured
to serve `main` and `/ (root)`. Editing Markdown on GitHub alone does not
regenerate the pages; the build must run before publishing the changes.

If the website still shows text you removed from Markdown, the generated HTML
may still contain the previous version. Rebuild and push the generated files,
then wait for the repository's Pages deployment to finish before refreshing.

## Add the next daily report

From **12 November 2026**, the combined task is split into three focused tasks:
arXiv papers, astrophysical alerts, and science news. Each starts on weekdays at
**08:00 Europe/Berlin**. They save independent parts; the last finishing task
assembles and publishes one complete dated report. Follow
[`docs/split-workflow.md`](docs/split-workflow.md) for the handoff, concurrency,
coverage audit and recovery rules. This supersedes the single-task delivery
workflow below while preserving the scientific and website requirements.

From 14 October 2026, a new Daily Physics Journal Club task is configured to
prepare the report in its current conversation and publish it to this repository.
The connected GitHub App was installed on 14 October to provide repository
access for publishing. The recurring task starts at **08:00 Europe/Berlin**,
beginning 15 October, with daylight-saving
changes handled by that timezone. The previous conversation's task is paused.
The 14 October report was prepared manually as the first report of this workflow.

The scheduled task must run the build and publish the generated files; the
website itself does not read conversations. It must verify the Pages deployment
and state any publishing failure in the chat instead of claiming success.
The source and editorial checks are documented in
[`docs/daily-workflow.md`](docs/daily-workflow.md).

1. Prepare the complete report for the intended listing date, or obtain the
   complete report from the current Journal Club conversation.
2. Add `content/YYYY-MM-DD.md`, following an existing file's JSON front matter
   and Markdown structure. Set `date`, `kind`, `description`, `scope`, `topics`,
   and `papers`. Daily titles and issue numbers are not used.
3. Match each paper's metadata `id` to a `<!-- paper:... -->` marker in the body.
   Keep paper titles, authors, links, equations, uncertainties, and corrections.
   Do not invent missing report content or paper dates.
4. Present each assessment under `##### History`, following the 22 September
   report. Omit personalized reading advice and conversational wording.
   Preserve the scientific summaries, equations, caveats, and source links.
   Reports from earlier dates retain their content until deliberately edited.
5. Rebuild, check the pages, search, and downloads, then commit and push.

The homepage introduces the journal club; its latest-report link and date update
automatically. The existing `editions/`
folder is retained only as a compatible URL for generated Markdown downloads;
the website calls each daily entry a **report**. Edit `content/`, because builds
overwrite the generated downloads and HTML.

For a news-only update, use the requested news-report date, set `kind` to
`Science news`, keep `papers` empty, and set `news_count` to the number of
news subsections. Include only the verified science-news body, with its source
links and equations. The dated page displays that body, and archive rows show
the news-section count. News updates do not add entries to the paper search.

## Astrophysical Alerts and Science News

Public reports separate **Astrophysical Alerts** from **Science News**.
Use `### Astrophysical Alerts` for astrophysical event detections, candidate
alerts, follow-ups, revised localizations, classifications, corrections and
retractions. Group reports of one event together. This section covers neutrinos,
gamma rays, X-rays, gravitational waves, cosmic rays and related transient events;
it excludes general instrument announcements and scientific-community news.

Use `### Science News` for all other science news: instrument and mission results,
awards, notable deaths, meetings, scientific-community developments and research
across mathematics, AI, biology, genetics, chemistry, geology, neuroscience,
medicine and other disciplines. The research scope previously called Science
Radar remains fully included here, with deliberate searches across those fields.
Do not restore a separate Science Radar heading in future reports.

Use `####` for individual stories. In JSON metadata, `alerts_count` counts alert
stories and `news_count` counts every Science News story, including other-science
research. Keep the counts separate from selected arXiv papers and full listing
totals. Preserve direct references, publication and observation dates, evidence
status and limitations. Present disputed claims and competing interpretations
neutrally; distinguish preprints and preliminary results from established findings.

The homepage and daily jump buttons link to these sections. Archive rows display
alert and news counts separately. These stories stay outside the arXiv paper-search
records. The split-task schema and publication protocol are documented in
[`docs/split-workflow.md`](docs/split-workflow.md).

## Dates and public writing

Use the arXiv listing date for the paper selection, rather than the date on
which the chat report was generated. The site uses the UTC listing-day
convention: a Thursday-evening Eastern announcement appears under Friday.
Check submission histories and the announcement schedule, and use an actual
listing record when available; moderation can delay an announcement.
Do not treat submission dates and announcement dates as interchangeable.

The original 12–13 September selections are consolidated into 10 September
(2 papers) and 11 September (11 papers), with each arXiv ID included once.
The [date audit](docs/date-audit-2026-09-10-11.md) records the sources and basis
for this grouping. News retained from the weekend has explicit 12 and
13 September headings; the withdrawn SVOM trigger includes the 14 September
correction. Old page links route to the corresponding paper or news section.

Keep each report's description statistical. Distinguish the number of
**selected papers** from the number of **new primary submissions in the full
listings**. For selection counts, count each paper once by its primary arXiv
category. Do not derive arXiv categories from the site's topic tags, count
cross-listings twice, invent missing totals, or imply the selection is the
entire daily listing. `statistics` metadata records the count basis.

Write for a public reader: omit conversational introductions, personal
reading advice, chat history, and subjective filler. Replace relative phrases
such as “today,” “yesterday,” and “this morning” with exact dates where the
chronology matters. Keep scientific findings, caveats, equations, corrections,
and direct source links. Preserve announcement dates separately from dates of
later news or follow-up observations.

Omit general notices that no new result appeared in a topic, that no story
passed a selection threshold, or that an already-covered result is not repeated.
Use the introduction for selection statistics. Omit sections with no substantive
content. Retain scientific null results, observation-specific non-detections,
and limitations that help readers interpret a paper or a reported event.

## Homepage and reader feedback

The homepage introduction and feedback form are in the home section of
`scripts/build_archive.py`. Edit this source and rebuild; `index.html` is generated.
The introduction remains the homepage when a new daily report is added.

Reader suggestions use the repository's public GitHub Issues. The form opens
GitHub with the reader's title and text filled in, where they sign in, review,
and submit the issue themselves. It works without JavaScript and requires no
server or credentials in the website. The form explains that feedback is public
and that a GitHub account is required. It does not submit an issue on its own.

Read and respond to feedback at <https://github.com/afesmaeili/J.C./issues>.

## Daily opening and listing totals — 11 November 2026

Begin each public daily report with one sentence giving the verified number of **new primary submissions** in that UTC arXiv listing for astro-ph, hep-ph, hep-ex, hep-th, gr-qc, nucl-ex and nucl-th. Exclude cross-lists and replacements; include HE/CO subcounts where verified. These are listing totals, separate from selected-paper statistics. Use dated catchup pages, not a mutable /new URL. If the counts cannot be checked, state that briefly rather than substituting selection counts or inventing zeroes.

The arxiv handoff must include `listing_statistics`: `date`, `basis: "new_primary_submissions"`, a `counts` mapping containing all seven categories, dated primary `sources`, and `verified_at`. Optional `astro_subcategories` records verified primary-category breakdowns. The assembler validates the date and count types.

Do not repeat the multi-paragraph source-check/date-control/partial-coverage preamble on each public page. General methodology appears on the homepage. Keep exact cutoffs, source URLs, date distinctions, actual screening scope and specific retrieval gaps in `source_audit` metadata (and each task's coverage field). Keep scientifically material limitations beside the affected paper or news story. A missing source must never be described as verified absence of news. Preserve historical audit information when simplifying an existing opening; do not erase it.


## Public paper presentation

Public report pages use neutral editorial prose. Begin with the verified category
listing totals, then the selected papers. Do not display production notes such as
"retrospective expansion", "added on [review date]", "revised edition", or a
conversation about what was originally included. Keep editorial revision dates
and change history in source_audit metadata; retain actual submission, version,
publication and observation dates beside the scientific content. Scientific
corrections and limitations remain explicit.

Each paper is rendered as an initially collapsed entry showing its bibliographic
title and authors. Opening the entry reveals its complete study and History.
Continue writing ordinary Markdown with the existing paper anchors and metadata;
the build supplies the disclosure markup. Preserve deep links, full-text search,
complete Markdown downloads and full-content printing. Do not write HTML details
elements or manual expand/collapse instructions into the report source.
